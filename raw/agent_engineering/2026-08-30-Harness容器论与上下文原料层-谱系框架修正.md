# Harness 容器论与"上下文原料层"：企业 Know-how 谱系框架修正

**整理日期**：2026-08-30
**背景**：群友对之前"四层谱系"框架的理论修正 + 《办公Agent大战，重点不是Agent》一文的上下文论点，对话中综合分析
**来源**：群聊讨论 + [[raw/agents/办公Agent大战，重点不是Agent]]

## 群友的框架修正（原文）

> Harness 不是知识分层里的一层，是这几层的容器。行业公式是 Agent = Model + Harness。Harness 指模型之外的一切（工具调用循环、context 管理、memory、可观测性）。所以更准确的图景是：模型权重是一侧，Harness 是另一侧 -- RAG、memory、continual learning 都是装在 Harness 里的组件，不是跟 Harness 并列的一层。
>
> 这几层与其说是"layer"（数据必须依次穿过的 architecture layer），不如说是同一个问题（"agent 怎么变强"）的几种不同机制，区别在于改动发生在哪、成本多高：RAG 改在外部语料，memory 改在外部持久存储，权重训练改在模型内部。生产系统一般是混用，不是选一个。
>
> 业界现在的叫法可以对照一下：
> 1. RAG 现在多被并入更大概念 context engineering下面；"记忆/经验积累"这层更标准的说法是 agent memory（分 episodic/semantic/procedural）；
> 2. 中间那层（持续学习/世界模型式的东西）业界也没共识，分成两派—— 一派是 training-free 的 test-time/continual learning（本质是 memory 套了层 RL 话术），另一派是真做参数更新但做得很轻很快（LoRA 快节奏），两派互相不认对方是"正统"；
> 3. 权重训练这层标准叫法是 post-training（SFT/RLHF/DPO/GRPO/RLVR），Agent Lightning 这类"把 harness 轨迹变训练数据"的路子，业界叫 agentic RL post-training 或 rollout-as-a-service。

## 对话中的分析

### 一、Harness 容器论是对之前框架的合理修正

之前"四层谱系"（①RAG②Harness③世界模型④权重）存在逻辑瑕疵：②和③④不是同一维度上的选项。②讲的是"改动发生在哪个容器里"，③④讲的是"要不要改模型参数"。修正后的表述——Agent = Model + Harness，RAG/memory/continual learning 都是装在 Harness 里的组件——更准确。原框架容易让人误以为这是必须依次穿过的流水线，实际是同一问题（Agent怎么变强）的几种并存机制，选哪个只是"改动位置"和"成本"的权衡，生产系统本就是混用。

### 二、术语映射与已有案例的对号

- **"training-free test-time/continual learning"派** = NeoCognition（声称做 world model，5个月零论文零benchmark，本质是"memory套RL话术"这个判断精准戳中 NeoCognition 最大可疑点）
- **"真做参数更新但很轻很快（LoRA快节奏）"派** = 暂无特别对号的已查案例；AgensFlow 反而是反例——连LoRA都没做，UCB1老虎机纯调度不碰权重，比两派都更保守
- **"agentic RL post-training / rollout-as-a-service"** = 精确命中 Agent Lightning——把 Harness 轨迹转成训练数据的做法

**补充精度**：Agent Lightning 的 reward 信号来自 SWE-bench 这类可验证的任务结果（跑没跑通、测试过没过），不是人类偏好打分，应归入 **RLVR**（Reinforcement Learning from Verifiable Rewards）子类，不是 RLHF/DPO 那挂——这个区分不是抠字眼，RLVR 是这两年把 agentic RL 做到低成本可复现的关键前提（有确定性对错，不需要昂贵人类标注）。

### 三、缺口：上下文"原料层"先于机制层

群友框架讲的是"改动发生在哪、成本多高"，隐含前提是**已经有干净的上下文可以喂给这些机制**。但《办公Agent大战，重点不是Agent》一文的核心论点是：大部分企业根本没有这个前提——上下文碎片散落在群聊、临时会议、口头交流里，从未被结构化沉淀过。

**这意味着一个前置约束**：四种机制（RAG/memory/harness配置/权重训练）没有一种能解决"原料不存在"这个问题——RAG查不到没被记录的东西，memory攒不出没发生过的交互，权重训练更不用说。飞书的护城河论点：把"上下文沉淀"这个前置步骤，通过云文档/多维表格/评论留痕做成工作过程的副产品，不需要事后搬运。

这与 [[raw/agents/2026-08-29-Cisco-MyAgent-企业Agent架构问答分析|Cisco Circuit 案例]] 也对得上——Circuit 好用的前提是 Cisco 自己数字化基础打得早、打得深（内部平台从2023年就开始建），普通企业没这个底子，四层机制再精妙也没有原料可喂。

**修正后的完整图景是五层，不是四层**：**原料层（上下文能不能被结构化捕获）→ Model+Harness容器 → 容器内的RAG/memory/权重训练机制**。前面讨论的都是"容器里怎么变强"，办公Agent一文讲的是"容器外面有没有东西能喂进去"——这是更前置、更难绕过的瓶颈，大概率是解释"为什么个人Agent好用、企业Agent还没雏形"最直接的原因。

## 办公Agent文章其他关键论点（背景整理）

- **模型不是护城河，Harness也不是**——OpenAI已开源Codex Harness，各家Harness终将同质化
- **上下文是真正的战场**——企业上下文极端复杂（同店口径/门店口径/线上线下/退货计不计入等统计口径分歧），个体用户的上下文装在脑子和硬盘里成本几乎为零，企业上下文分散在ERP/POS/电商后台/会员系统/物流系统，各有各的统计口径
- **飞书的结构性优势**：云文档/多维表格/智能纪要本身是AI Native工作方式，工作"过程"（评论、修改、讨论）全部在线留痕，不像同类产品只把文档当结果
- **企业级Agent的可靠性两指标**：① Token额度管理（Uber四个月烧完全年预算、Meta内部有人一个月烧50万美元——均为文章引用，未独立核实）② 数据安全（芯片设计等行业对数据泄露极端保守）
