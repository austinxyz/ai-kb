前言

我们正在经历的，可能是软件工程有史以来最陡峭的一段曲线

AGI 什么时候到来，仍然没有真正的共识。有人说三年，有人说五到十年，也有人认为还需要更久。

但对工程师来说，另一个变化已经足够真实：AI 不再只是补全代码的工具，正在变成能够读项目、改文件、运行命令、调用工具、并行探索方案的 Agent。

这意味着，软件工程里的稀缺性正在重新分配。

过去，代码很贵。一个功能要写很久，一个原型要搭很久，一个实验要等很久。今天，代码生成正在变得越来越便宜。真正变贵的，是判断：需求是否真实，方案是否合理，架构是否稳固，边界是否清楚，失败后能不能回滚，生成出来的东西能不能被验证。

过去九年，AI 的能力曲线几乎没有给我们太多喘息时间。

2017 年，Transformer 架构论文发表。此后，模型规模、训练方法、推理能力、上下文窗口、工具调用、多模态能力不断推进。每一轮突破之后，都会有人说“差不多到头了”。但下一轮又会证明，我们看到的往往不是终点，而是新曲线的起点。

而现在，我们正站在另一条曲线的起点：从 AI 写代码，到 AI 执行工程任务。

这条曲线真正改变的，不只是编程效率，而是工程组织方式。

  

PART 01

  

过去一年多，边界被连续推开

  

  

2024 年，公司开始推广使用 GitHub Copilot。很多工程师一开始并不兴奋。至少在我和身边同事的日常使用里，它更多还是被当作一个更聪明的 Tab 补全：你写一行，它补一行；你开个头，它接下去。它有用，但还没有真正改变我们对“软件工程”的理解。

2024 年 8 月初，我接触到了 Cursor。真正让我震撼的，是 Composer 模式。

它突破了 Copilot 在我心里的边界。它不再只是补全单行代码，而是可以同时理解和修改多个文件。我用它做了一个 2048 游戏：把截图发过去，它帮我设计 UI；我写 spec，它理解我的意图，帮我实现；过程中有新想法涌现，它配合我不断调整。

那一刻，我第一次明显感觉到：AI 不再只是一个补全器，而开始像一个能触碰项目结构的协作者。

但 Composer 模式也暴露了一个问题：它并不可靠地知道自己的工作做到哪里了。

你说“做完了”，追问一句“再检查一下”，它又能列出一堆没做的部分。它可以生成计划，也可以在追问时重新审视结果，但它并不天然拥有稳定的任务状态，也不天然拥有独立的验收标准。

后来我才意识到，我反复说“再检查一遍”，本质上是在用人工方式补一个缺失的 Harness。

那时候我还没有给这件事命名。我只知道，如果不反复检查，AI 很容易把“看起来完成”当成“真正完成”。

2025 年 2 月，Claude Code 以研究预览的形式出现。

它和传统 IDE 插件不一样。它从命令行进入项目，能够读代码、改文件、运行测试、提交代码。Agent 第一次不只是“建议下一行”，而是开始进入整个工程现场。

这带来的变化很深。

过去，AI 工具更多停留在编辑器内部；现在，它开始接触文件系统、终端、测试框架、版本控制和项目结构。换句话说，它不只是写代码，而是在执行工程动作。

同一年，OpenAI 推出 Codex，把云端代码 Agent、多任务并行和沙箱执行推到台前。到 2026 年，Codex app 又进一步把多个 coding agent 的并行调度做成产品形态。

不同公司的路径并不相同，但它们共同指向一个趋势：IDE 不再是唯一边界。Agent 开始直接面对项目、命令、测试、版本控制和团队流程。

这是范式上的变化。

从 Tab 补全，到聊天；从单文件编辑，到跨文件编辑；从编辑器里的建议，到命令行里的执行；从单个 Agent，到多个 Agent 并行工作。

短短一年多，软件工程的工作界面被连续推开了好几次。

  

PART 02

  

一把梭的诱惑，与它的代价

  

  

随着 Agent 能力增强，权限也开始被不断放开。

社区里出现了所谓 “YOLO mode” 的用法：少问人，直接执行，一把梭。

它很诱人。

你不用反复确认，不用每一步都批准，不用盯着它改了哪个文件。你只需要给出目标，然后看着 Agent 一路跑下去。对于习惯了等待编译、等待 review、等待排期的工程师来说，这种速度几乎令人上瘾。

但我很快发现，结果往往并不好。

一步错，后面每一步都可能建立在错误基础上。一个不恰当的抽象，会引出更多不恰当的修改；一个误判的需求，会导致整个实现方向偏掉；一个失败的工具调用，如果没有被正确处理，可能会让 Agent 在错误路径上反复尝试。

最后你得到的不是一个完成的功能，而是一团看似努力过、实际很难接手的代码。

这个失败让我意识到：Agent 的问题不只是“聪不聪明”，而是有没有权限边界、阶段验收、失败回滚和退出条件。

AI 可以快思考，但人不能放弃慢判断。

过去我们常说，人要避免过度管理。但在 Agent 系统里，真正的问题不是“管得太多”，而是“没有把判断设计进系统”。

如果所有判断都留在人的脑子里，人就会被上下文切换压垮。

如果所有判断都交给模型，错误就会在高速执行中被放大。

所以，人和 AI 的分工必须重新定义：AI 做执行、探索和快速生成；人做判断、约束和最终验收。更进一步，人不能只在脑子里判断，而要把判断外化成流程、规则、验证器、权限边界和监控机制。

这就是 Harness Engineering 要解决的问题。

  

PART 03

  

Vibe coding 之后，真正困难的事情浮出水面

  

  

2025 年初，Andrej Karpathy 提出了 vibe coding。

这个词一出来，争议很大。很多人觉得这不严肃：不认真读代码，不逐行理解细节，说一句话让 AI 去做，然后凭感觉调整结果，这算哪门子编程？

但这个词之所以流行，恰恰是因为它说中了某种真实体验。

当模型足够强，代码生成足够快，开发者确实会开始改变工作方式。你不再从第一行代码开始构造程序，而是从意图、效果、反馈和迭代开始推动系统成形。你描述目标，观察结果，调整方向，让模型继续生成，再根据结果做判断。

这不是传统意义上的手写代码。

但它也绝不是“随便说几句话”。

真正困难的事情，反而在这个时候浮出水面。

你要判断需求是不是真实需求。你要判断 AI 给出的方案是不是合理架构。你要判断什么时候让它继续，什么时候必须打断。你要判断一个实现是“刚好能跑”，还是“可以进入长期维护”。你要在多个上下文之间切换，却不能丢掉工程判断。你要知道哪些地方可以放手，哪些地方必须收紧。

这比想象中难得多。

因为代码生成变快之后，人的判断力会成为瓶颈。

过去，代码写得慢，人的思考有时间跟上。今天，Agent 可以在几分钟内改几十个文件、跑多轮尝试、生成多个方案。上下文切换之间，大量决策堆积起来。你还没来得及想清楚上一轮变化，下一轮输出已经到眼前。

这时，真正稀缺的不是“会不会写代码”，而是能不能保持判断清醒。

2026 年初，Peter Steinberger 和 OpenClaw 成为一个很有象征意义的案例。OpenClaw 未必是第一个本地 Agent，但它表达了一个清楚的趋势：Agent 不再只待在代码编辑器里，它开始进入本机、通讯入口和个人工作流。

这提醒我，AI coding 的边界正在外扩。

未来的问题不只是“AI 能不能写代码”，而是“AI 能不能在真实环境中安全地做事”。

一旦 Agent 开始接触真实项目、真实文件、真实命令、真实账户和真实协作流程，问题就不再只是 prompt engineering，而是 engineering。

  

PART 04

  

我曾经省错了东西

  

  

我回看自己的 2025 年 commit 记录，不到 4000 次。

这个数字当然不能直接代表产出。有人会 squash commit，有人主要在私有仓库工作，有人用很少的 commit 做出很高价值的设计。但它提醒了我一件事：我在使用 AI 的方式上，仍然偏保守。

反思原因，有两点。

  

  

第一，我那时候舍不得用 token

很多本该让 AI 探索的事情，我没有放手。很多本该让 Agent 并行尝试的方向，我选择自己慢慢想。表面上看，我是在省成本；实际上，我是在用工程师最贵的时间，去省相对便宜得多的推理成本。

这背后是一个认知问题。

AI coding 的核心逻辑不是“让 AI 替你思考一切”，而是“用你的时间做判断，让 AI 的时间做执行”。

你的时间才是最贵的资源。

  

  

第二，我缺少系统的方法论

我不知道如何并发控制多个 Agent，不知道如何让判断更精准地外化，不知道如何设置阶段性验收，不知道如何避免 Agent 陷入无限循环，也不知道如何用 token 杠杆放大工程产出。

那时我还常常把问题归因于模型不够强。

后来我意识到，很多时候不是模型不够强，而是我没有给它设计工作边界和验证机制。

Agent 崛起后，token 消耗重新成为焦点。

一次 Agent 任务往往包含规划、检索、工具调用、失败重试和验证，天然比单轮聊天消耗更多 token。但 token 不应该变成新的虚荣指标。真正的问题不是“烧了多少 token”，而是这些 token 是否换来了更快的反馈、更可靠的验证、更少的人类上下文切换，以及更高质量的工程结果。

不要省错东西。

该省的不是 token，而是人的混乱、返工和误判。

  

PART 05

  

真正变贵的，不是代码

  

  

硅谷有句老话：

  

Talk is cheap. Show me the code.

  

  

在 AI coding 时代，这句话的含义变了。

代码生成变得非常便宜，但好代码依然非常难。甚至可以说，因为代码生成变便宜了，好代码变得更难了。

过去，写代码本身就是一道门槛。一个想法如果不够清楚，往往写着写着就暴露出来。今天，AI 可以很快把模糊想法变成一堆看似完整的代码。它会让一个不成熟的需求迅速膨胀成一个不成熟的系统。

所以，真正昂贵的东西变成了判断。

架构是否合理？需求是否真实？抽象是否过早？边界是否清楚？测试是否覆盖关键风险？失败后能否回滚？这个实现三个月后还能不能维护？

这些判断不会因为 AI 出现而消失。

恰恰相反，它们变得更重要了。

人和 AI 的分工正在变化。AI 做快思考，做执行，做探索；人做慢思考，做判断，做审美。你的品味、你的工程直觉、你多年踩坑后形成的边界感，反而变成了最稀缺的东西。

但这里有一个陷阱。

AI 生成太快，你的判断力可能成为瓶颈。上下文切换之间，决策不断堆积，脑子越来越乱，深度思考变得奢侈。你以为自己在指挥 Agent，实际上可能只是被 Agent 的输出牵着走。

怎么破？

不是让人重新慢慢手写一切，也不是把所有决策权都交给 AI。

真正的答案，是把判断工程化。

把判断变成可执行的规范。把风险变成可检查的条件。把权限变成明确的边界。把循环变成有退出条件的流程。把验证交给独立机制，而不是只相信生成者的自我评价。把个人经验变成团队可以共享的制度。

这就是我写这本书的原因。

  

PART 06

  

什么是 Harness Engineering

  

  

Harness 这个词，可以理解为“安全带”“约束装置”“测试线束”或者“工程护栏”。它不是为了限制 AI 的能力，而是为了让 AI 的能力在真实系统中可控地释放。

Harness Engineering 研究的不是“怎样让 AI 写更多代码”，而是“怎样让不稳定的 AI Agent 在真实工程系统里稳定地产生价值”。

它接受一个基本事实：

AI 是强大的工具，但不是可靠的组件。

模型会幻觉，会遗漏，会过度自信，会在上下文压力下丢失约束，会把“看起来合理”误当成“已经验证”。Agent 会陷入循环，会误用工具，会在权限过大的情况下制造更大范围的错误。多个 Agent 同时工作时，还会出现结论冲突、状态分裂、重复劳动和责任不清。

这些问题不能只靠更好的 prompt 解决。

Prompt 很重要，但 prompt 不是系统。

一个可靠的 Agent 系统，需要 Harness。

它需要明确的输入边界、工具权限、任务状态、循环结构、退出条件、独立验证、监控机制、失败回滚和团队规则。

这本书的核心，是五条 Harness Engineering 原则：

1. 模型是不稳定组件，所以关键输出必须被验证  
    不要因为回答流畅，就认为它正确。不要因为代码能跑，就认为它可靠。不要因为 Agent 说“完成了”，就认为任务真的完成了。
    
2. Query Loop 是 Agent 的心跳，所以必须有明确的退出条件  
    一个没有退出条件的 Agent，看似勤奋，实则危险。它会不断尝试、不断修补、不断制造新的上下文，直到人类失去判断力。
    
3. 工具是执行接口，所以必须遵循最小权限原则  
    Agent 能做什么，比它知道什么更危险。读文件、写文件、运行命令、访问网络、提交代码、调用内部系统，每一个能力都应该被审慎授予。
    
4. 验证必须独立，所以不能让生成者成为唯一验收者  
    写代码的 Agent 可以自查，但不能只靠它自查。真正可靠的系统，需要测试、静态检查、规则引擎、独立 Agent、人类 review 或其他外部机制参与验证。
    
5. 团队约束比个人手感重要，所以多 Agent 协作需要明确规则
    

一个高手可以凭经验驾驭一个 Agent，但团队不能只靠个人手感。团队需要共享的协议：任务如何拆分，状态如何同步，冲突如何解决，失败如何复盘，产出如何验收。

理解这五条原则，你就能理解为什么有些 Agent 系统可以稳定运行，而有些看起来强大，却总是在关键时刻掉链子。

  

PART 07

  

这本书解决什么问题

  

  

这本书不教你“如何用某个 AI 工具写代码”。

这类教程已经太多，而且工具变化太快。今天流行的按钮，明天可能就被新的交互方式替代；今天最强的模型，半年后也可能不再是默认选择。

这本书想回答一个更底层的问题：

如何让 AI Agent 真正可靠地工作？

模型输出不稳定怎么办？Agent 陷入无限循环怎么办？工具调用失败怎么办？多个 Agent 结论不一致怎么办？Agent 写出的代码看似能跑、实则不可维护怎么办？人类判断被大量上下文切换压垮怎么办？团队里每个人都用 Agent，但产出质量参差不齐怎么办？

这些问题不是某个工具的使用技巧，而是 AI 时代的软件工程问题。

读这本书需要一些编程基础，但不需要你懂机器学习，也不需要你用过某个特定的 AI 工具。我会从上下文窗口、token、工具调用、Agent loop 这些基础概念讲起，然后一步步进入更真实的工程场景。

读完这本书，你应该能够设计一个带完整 Harness 的代码审查 Agent，构建多 Agent 协作系统，设置工具权限和退出条件，建立独立验证机制，并为 Agent 系统设计持续可用的监控与复盘流程。

更重要的是，你会拥有一个思维框架。

面对任何新的 AI 编程工具，你不再只问：“它能不能帮我写代码？”

你会开始问：

它的输入边界在哪里？它能调用哪些工具？它如何知道任务完成？它的输出由谁验证？它失败后如何回滚？它如何和其他 Agent 协作？它如何进入团队流程，而不是只停留在个人实验？

这些问题，比某个具体工具的使用方法更长久。

  

PART 08

  

工具会变，工程思维不会变

  

  

这本书不是某个工具的手册。

工具会变，框架会变，模型会变，交互方式也会变。

也许今天我们还在谈 IDE 插件、命令行 Agent 和云端沙箱；明天，Agent 可能已经成为操作系统、浏览器、代码仓库、CI/CD 和企业工作流里的默认层。

但无论工具怎么变，有些工程问题不会消失。

不稳定组件如何接入可靠系统？高权限执行者如何被约束？快速生成的产物如何被验证？多个执行单元如何协作？失败如何被发现、限制和恢复？人的判断如何不被机器速度吞没？

这些问题不会因为模型变强而自动消失。

模型越强，越需要 Harness。

如果这本书能让你记住一件事，我希望是：

AI 是强大的工具，但不是可靠的组件。构建可靠的系统，需要工程思维。

希望你在 AI 编程的旅程中，少踩一些我踩过的坑。

Onebird

2026 年 4 月，于上海张江

  

我们正在经历的，可能是软件工程有史以来最陡峭的一段曲线

AGI 什么时候到来，仍然没有真正的共识。有人说三年，有人说五到十年，也有人认为还需要更久。

但对工程师来说，另一个变化已经足够真实：AI 不再只是补全代码的工具，正在变成能够读项目、改文件、运行命令、调用工具、并行探索方案的 Agent。

过去九年，AI 的能力曲线几乎没有给我们太多喘息时间。

而现在，我们正站在另一条曲线的起点：从 AI 写代码，到 AI 执行工程任务。

PART 09

  

过去一年多，边界被连续推开

  

  

2024 年，公司开始推广 GitHub Copilot。

很多工程师一开始并不兴奋。至少在我和身边同事的日常使用里，它更多还是被当作一个更聪明的 Tab 补全：你写一行，它补一行；你开个头，它接下去。它有用，但还没有真正改变我们对“软件工程”的理解。

2024 年 8 月底，我接触到了 Cursor。

真正让我震撼的，是 Composer 模式。

它突破了 Copilot 在我心里的边界。它不再只是补全单行代码，而是可以同时理解和修改多个文件。我用它做了一个 2048 游戏：把截图发过去，它帮我设计 UI；我写 spec，它理解我的意图，帮我实现；过程中有新想法涌现，它配合我不断调整。

那一刻，我第一次明显感觉到：AI 不再只是一个补全器，而开始像一个能触碰项目结构的协作者。

但 Composer 模式也暴露了一个问题：它并不可靠地知道自己的工作做到哪里了。

他说“我做完了”，你追问一句“再检查一下，到底有没有真的全部做完”，它又能列出一堆没做的部分。它可以生成计划，也可以在追问时重新审视结果，但它并不天然拥有稳定的任务状态，也不天然拥有独立的验收标准。

后来我才意识到，我反复说“再检查一遍”，本质上是在用人工方式补一个缺失的 Harness。

那时候我还没有给这件事命名。我只知道，如果不反复检查，AI 很容易把“看起来完成”当成“真正完成”。

2025 年 2 月，Claude Code 以研究预览的形式出现。

它和传统 IDE 插件不一样。它从命令行进入项目，能够读代码、改文件、运行测试、提交代码。Agent 第一次不只是“建议下一行”，而是开始进入整个工程现场。

这带来的变化很深。

过去，AI 工具更多停留在编辑器内部；现在，它开始接触文件系统、终端、测试框架、版本控制和项目结构。换句话说，它不只是写代码，而是在执行工程动作。

同一年，OpenAI 推出 Codex，把云端代码 Agent、多任务并行和沙箱执行推到台前。到 2026 年，Codex app 又进一步把多个 coding agent 的并行调度做成产品形态。

不同公司的路径并不相同，但它们共同指向一个趋势：IDE 不再是唯一边界。Agent 开始直接面对项目、命令、测试、版本控制和团队流程。

这是范式上的变化。

从 Tab 补全，到聊天；从单文件编辑，到跨文件编辑；从编辑器里的建议，到命令行里的执行；从单个 Agent，到多个 Agent 并行工作。

短短一年多，软件工程的工作界面被连续推开了好几次。

  

PART 10

  

一把梭的诱惑，与它的代价

  

  

随着 Agent 能力增强，权限也开始被不断放开。

社区里出现了所谓 “YOLO mode” 的用法：少问人，直接执行，一把梭。

它很诱人。

你不用反复确认，不用每一步都批准，不用盯着它改了哪个文件。你只需要给出目标，然后看着 Agent 一路跑下去。对于习惯了等待编译、等待 review、等待排期的工程师来说，这种速度几乎令人上瘾。

但我很快发现，结果往往并不好。

一步错，后面每一步都可能建立在错误基础上。一个不恰当的抽象，会引出更多不恰当的修改；一个误判的需求，会导致整个实现方向偏掉；一个失败的工具调用，如果没有被正确处理，可能会让 Agent 在错误路径上反复尝试。

最后你得到的不是一个完成的功能，而是一团看似努力过、实际很难接手的代码。

这个失败让我意识到：Agent 的问题不只是“聪不聪明”，而是有没有权限边界、阶段验收、失败回滚和退出条件。

AI 可以快思考，但人不能放弃慢判断。

过去我们常说，人要避免过度管理。但在 Agent 系统里，真正的问题不是“管得太多”，而是“没有把判断设计进系统”。

如果所有判断都留在人的脑子里，人就会被上下文切换压垮。

如果所有判断都交给模型，错误就会在高速执行中被放大。

所以，人和 AI 的分工必须重新定义：AI 做执行、探索和快速生成；人做判断、约束和最终验收。更进一步，人不能只在脑子里判断，而要把判断外化成流程、规则、验证器、权限边界和监控机制。

这就是 Harness Engineering 要解决的问题。

  

PART 11

  

Vibe coding 之后，真正困难的事情浮出水面

  

  

2025 年初，Andrej Karpathy 提出了 vibe coding。

这个词一出来，争议很大。很多人觉得这不严肃：不认真读代码，不逐行理解细节，说一句话让 AI 去做，然后凭感觉调整结果，这算哪门子编程？

但这个词之所以流行，恰恰是因为它说中了某种真实体验。

当模型足够强，代码生成足够快，开发者确实会开始改变工作方式。你不再从第一行代码开始构造程序，而是从意图、效果、反馈和迭代开始推动系统成形。你描述目标，观察结果，调整方向，让模型继续生成，再根据结果做判断。

这不是传统意义上的手写代码。

但它也绝不是“随便说几句话”。

真正困难的事情，反而在这个时候浮出水面。

你要判断需求是不是真实需求。你要判断 AI 给出的方案是不是合理架构。你要判断什么时候让它继续，什么时候必须打断。你要判断一个实现是“刚好能跑”，还是“可以进入长期维护”。你要在多个上下文之间切换，却不能丢掉工程判断。你要知道哪些地方可以放手，哪些地方必须收紧。

这比想象中难得多。

因为代码生成变快之后，人的判断力会成为瓶颈。

过去，代码写得慢，人的思考有时间跟上。今天，Agent 可以在几分钟内改几十个文件、跑多轮尝试、生成多个方案。上下文切换之间，大量决策堆积起来。你还没来得及想清楚上一轮变化，下一轮输出已经到眼前。

这时，真正稀缺的不是“会不会写代码”，而是能不能保持判断清醒。

2026 年初，Peter Steinberger 和 OpenClaw 成为一个很有象征意义的案例。OpenClaw 未必是第一个本地 Agent，但它表达了一个清楚的趋势：Agent 不再只待在代码编辑器里，它开始进入本机、通讯入口和个人工作流。

这提醒我，AI coding 的边界正在外扩。

未来的问题不只是“AI 能不能写代码”，而是“AI 能不能在真实环境中安全地做事”。

一旦 Agent 开始接触真实项目、真实文件、真实命令、真实账户和真实协作流程，问题就不再只是 prompt engineering，而是 engineering。

  

PART 12

  

我曾经省错了东西

  

  

我回看自己的 2025 年 commit 记录，不到 4000 次。

这个数字当然不能直接代表产出。有人会 squash commit，有人主要在私有仓库工作，有人用很少的 commit 做出很高价值的设计。但它提醒了我一件事：我在使用 AI 的方式上，仍然偏保守。

反思原因，有两点。

  

  

第一，我那时候舍不得用 token

很多本该让 AI 探索的事情，我没有放手。很多本该让 Agent 并行尝试的方向，我选择自己慢慢想。表面上看，我是在省成本；实际上，我是在用工程师最贵的时间，去省相对便宜得多的推理成本。

这背后是一个认知问题。

AI coding 的核心逻辑不是“让 AI 替你思考一切”，而是“用你的时间做判断，让 AI 的时间做执行”。

你的时间才是最贵的资源。

  

  

第二，我缺少系统的方法论

我不知道如何并发控制多个 Agent，不知道如何让判断更精准地外化，不知道如何设置阶段性验收，不知道如何避免 Agent 陷入无限循环，也不知道如何用 token 杠杆放大工程产出。

那时我还常常把问题归因于模型不够强。

后来我意识到，很多时候不是模型不够强，而是我没有给它设计工作边界和验证机制。

Agent 崛起后，token 消耗重新成为焦点。

一次 Agent 任务往往包含规划、检索、工具调用、失败重试和验证，天然比单轮聊天消耗更多 token。但 token 不应该变成新的虚荣指标。真正的问题不是“烧了多少 token”，而是这些 token 是否换来了更快的反馈、更可靠的验证、更少的人类上下文切换，以及更高质量的工程结果。

不要省错东西。

该省的不是 token，而是人的混乱、返工和误判。

  

PART 13

  

真正变贵的，不是代码

  

  

硅谷有句老话：

  

Talk is cheap. Show me the code.

  

  

在 AI coding 时代，这句话的含义变了。

代码生成变得非常便宜，但好代码依然非常难。甚至可以说，因为代码生成变便宜了，好代码变得更难了。

过去，写代码本身就是一道门槛。一个想法如果不够清楚，往往写着写着就暴露出来。今天，AI 可以很快把模糊想法变成一堆看似完整的代码。它会让一个不成熟的需求迅速膨胀成一个不成熟的系统。

所以，真正昂贵的东西变成了判断。

架构是否合理？需求是否真实？抽象是否过早？边界是否清楚？测试是否覆盖关键风险？失败后能否回滚？这个实现三个月后还能不能维护？

这些判断不会因为 AI 出现而消失。

恰恰相反，它们变得更重要了。

人和 AI 的分工正在变化。AI 做快思考，做执行，做探索；人做慢思考，做判断，做审美。你的品味、你的工程直觉、你多年踩坑后形成的边界感，反而变成了最稀缺的东西。

但这里有一个陷阱。

AI 生成太快，你的判断力可能成为瓶颈。上下文切换之间，决策不断堆积，脑子越来越乱，深度思考变得奢侈。你以为自己在指挥 Agent，实际上可能只是被 Agent 的输出牵着走。

怎么破？

不是让人重新慢慢手写一切，也不是把所有决策权都交给 AI。

真正的答案，是把判断工程化。

把判断变成可执行的规范。把风险变成可检查的条件。把权限变成明确的边界。把循环变成有退出条件的流程。把验证交给独立机制，而不是只相信生成者的自我评价。把个人经验变成团队可以共享的制度。

这就是我写这本书的原因。

  

PART 14

  

什么是 Harness Engineering

  

  

Harness 这个词，可以理解为“安全带”“约束装置”“测试线束”或者“工程护栏”。它不是为了限制 AI 的能力，而是为了让 AI 的能力在真实系统中可控地释放。

Harness Engineering 研究的不是“怎样让 AI 写更多代码”，而是“怎样让不稳定的 AI Agent 在真实工程系统里稳定地产生价值”。

它接受一个基本事实：

AI 是强大的工具，但不是可靠的组件。

模型会幻觉，会遗漏，会过度自信，会在上下文压力下丢失约束，会把“看起来合理”误当成“已经验证”。Agent 会陷入循环，会误用工具，会在权限过大的情况下制造更大范围的错误。多个 Agent 同时工作时，还会出现结论冲突、状态分裂、重复劳动和责任不清。

这些问题不能只靠更好的 prompt 解决。

Prompt 很重要，但 prompt 不是系统。

一个可靠的 Agent 系统，需要 Harness。

它需要明确的输入边界、工具权限、任务状态、循环结构、退出条件、独立验证、监控机制、失败回滚和团队规则。

这本书的核心，是五条 Harness Engineering 原则：

1. 模型是不稳定组件，所以关键输出必须被验证  
    不要因为回答流畅，就认为它正确。不要因为代码能跑，就认为它可靠。不要因为 Agent 说“完成了”，就认为任务真的完成了。
    
2. Query Loop 是 Agent 的心跳，所以必须有明确的退出条件  
    一个没有退出条件的 Agent，看似勤奋，实则危险。它会不断尝试、不断修补、不断制造新的上下文，直到人类失去判断力。
    
3. 工具是执行接口，所以必须遵循最小权限原则  
    Agent 能做什么，比它知道什么更危险。读文件、写文件、运行命令、访问网络、提交代码、调用内部系统，每一个能力都应该被审慎授予。
    
4. 验证必须独立，所以不能让生成者成为唯一验收者  
    写代码的 Agent 可以自查，但不能只靠它自查。真正可靠的系统，需要测试、静态检查、规则引擎、独立 Agent、人类 review 或其他外部机制参与验证。
    
5. 团队约束比个人手感重要，所以多 Agent 协作需要明确规则
    

一个高手可以凭经验驾驭一个 Agent，但团队不能只靠个人手感。团队需要共享的协议：任务如何拆分，状态如何同步，冲突如何解决，失败如何复盘，产出如何验收。

理解这五条原则，你就能理解为什么有些 Agent 系统可以稳定运行，而有些看起来强大，却总是在关键时刻掉链子。

  

PART 15

  

这本书解决什么问题

  

  

这本书不教你“如何用某个 AI 工具写代码”。

这类教程已经太多，而且工具变化太快。今天流行的按钮，明天可能就被新的交互方式替代；今天最强的模型，半年后也可能不再是默认选择。

这本书想回答一个更底层的问题：

如何让 AI Agent 真正可靠地工作？

模型输出不稳定怎么办？Agent 陷入无限循环怎么办？工具调用失败怎么办？多个 Agent 结论不一致怎么办？Agent 写出的代码看似能跑、实则不可维护怎么办？人类判断被大量上下文切换压垮怎么办？团队里每个人都用 Agent，但产出质量参差不齐怎么办？

这些问题不是某个工具的使用技巧，而是 AI 时代的软件工程问题。

读这本书需要一些编程基础，但不需要你懂机器学习，也不需要你用过某个特定的 AI 工具。我会从上下文窗口、token、工具调用、Agent loop 这些基础概念讲起，然后一步步进入更真实的工程场景。

读完这本书，你应该能够设计一个带完整 Harness 的代码审查 Agent，构建多 Agent 协作系统，设置工具权限和退出条件，建立独立验证机制，并为 Agent 系统设计持续可用的监控与复盘流程。

更重要的是，你会拥有一个思维框架。

面对任何新的 AI 编程工具，你不再只问：“它能不能帮我写代码？”

你会开始问：

它的输入边界在哪里？它能调用哪些工具？它如何知道任务完成？它的输出由谁验证？它失败后如何回滚？它如何和其他 Agent 协作？它如何进入团队流程，而不是只停留在个人实验？

这些问题，比某个具体工具的使用方法更长久。

  

PART 16

  

工具会变，工程思维不会变

  

  

这本书不是某个工具的手册。

工具会变，框架会变，模型会变，交互方式也会变。

也许今天我们还在谈 IDE 插件、命令行 Agent 和云端沙箱；明天，Agent 可能已经成为操作系统、浏览器、代码仓库、CI/CD 和企业工作流里的默认层。

但无论工具怎么变，有些工程问题不会消失。

不稳定组件如何接入可靠系统？高权限执行者如何被约束？快速生成的产物如何被验证？多个执行单元如何协作？失败如何被发现、限制和恢复？人的判断如何不被机器速度吞没？

这些问题不会因为模型变强而自动消失。

模型越强，越需要 Harness。

如果这本书能让你记住一件事，我希望是：

AI 是强大的工具，但不是可靠的组件。构建可靠的系统，需要工程思维。

希望你在 AI 编程的旅程中，少踩一些我踩过的坑。
